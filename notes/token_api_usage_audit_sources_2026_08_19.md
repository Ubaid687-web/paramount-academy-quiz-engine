# Token and API Usage Audit Sources — 2026-08-19

## Official provider documentation

| Source | Verified finding | Consequence for this application |
| --- | --- | --- |
| Google Gemini API, [Context caching — Interactions API](https://ai.google.dev/gemini-api/docs/caching) | The Interactions API supports **implicit caching only**; no explicit cache objects can be created or managed through that API. Gemini 3.6 Flash implicit caching is enabled by default once input reaches 4,096 tokens. Cache-hit tokens are exposed through `usage.total_cached_tokens`. Google advises putting large shared content at the beginning and keeping a similar prefix across nearby requests. | The existing direct Gemini fallback can benefit only from automatic provider caching. Any explicit-cache proposal would require changing API families and must be assessed separately for source-safety, data retention, and reliability. |
| Google Gemini API, [Interactions API overview](https://ai.google.dev/gemini-api/docs/interactions-overview) | Implicit caching works in both stateful and stateless modes. `previous_interaction_id` can improve reuse of conversation history, but `store=false` prevents using that state. System instructions remain interaction-scoped and must be supplied for each request. | The application intentionally sends `store=false`; retaining it protects the current stateless, per-paper privacy boundary. Moving to server-side conversations would not be an automatic safe optimization. |

These are provider capability findings only. No provider caching setting, data-retention policy, or application prompt was changed during this report-only audit.

## Current implementation evidence

| Audit area | Current behavior | Audit interpretation |
| --- | --- | --- |
| Managed-provider output budget | The shared managed-provider client hard-codes `max_tokens: 32768` and a 128-token thinking budget for every request. Its exposed per-call `maxTokens`/`max_tokens` parameters are not applied to the outgoing payload. | There is no task-specific output ceiling today; 32,768 tokens is materially broader than the expected structured output for standard MCQ and printable-paper requests. Any tighter proposal must be tested against complete schema output and must never turn validation failures into silently shortened papers. |
| Gemini fallback output budget | The direct Interactions request supplies a JSON schema but no output-token cap. | The provider default controls output length. This protects against a premature truncation setting but provides no deliberate budget alignment or usage visibility. |
| MCQ source budgeting | `buildBudgetedSourceText` retains the full source when it is at most 24,000 characters. Above that, it splits on blank paragraphs or approximate 1,800-character sections, then picks evenly spaced first-to-last excerpts. | It is breadth-oriented sampling, **not semantic relevance ranking**. It can miss the textbook passage most relevant to a selected concept and therefore cannot safely be described as targeted selection. |
| Printable source budgeting | Printable generation divides the supplied source into equal word chunks, retains up to six chunks, and takes the first 1,500 characters of each. | This is deterministic coverage sampling, **not semantic relevance ranking**. It is a priority correctness risk before any further token reduction, even though scope-level source selection remains server-approved. |
| Static repeated context | Every MCQ request includes the fixed MCQ prompt, optional citation rules, shared style anchor, and a generated prior-history exclusion block. Every printable batch repeats its fixed printable prompt, shared style anchor, source title, prior-history exclusion, and source sections. The style anchor is bounded to six paper-pattern profiles and four examples. | The anchor is safety-relevant format guidance, so simply removing it is not acceptable. Gemini implicit caching can help only when the repeated prefix crosses the provider’s cache threshold and remains stable. |
| Redundant model calls | MCQ generation makes one provider call after an exact-result cache check. Printable papers deliberately batch pairs and make one model call per batch; the current bound is four pairs, so a 10-pair paper requires three calls. Retry calls are provider-failure recovery, not separate generation paths. | There is no accidental duplicate call in the MCQ path. Printable calls cannot be blindly consolidated to one because bounded batches constrain structured-output size and preserve batch-level diversity validation. |
| Actual token visibility | Provider responses can contain usage data, and the Gemini transport maps input/output/total usage into its response. However, generation telemetry and `generationJobs` persist only provider routing, retry/cache state, and character-count proxies—not input, output, cached, or total tokens. Portal Admin history exposes those character proxies only. | The requested token-usage view is **not currently available**. It is feasible as additive telemetry, but it needs a schema migration, job-update plumbing, history API/UI work, and a clear distinction between actual provider tokens, Gemini cache-hit tokens, and estimated character counts. |

### Observed 30-day job telemetry snapshot

The current database records 39 recent jobs. It contains **no actual token totals**, so it cannot establish costs or quota consumption. It shows 38 managed-provider jobs with an average recorded 2,120 input characters and 17 failed jobs, plus one successful Gemini fallback job with 2,425 recorded input characters. Exact-result cache hits were zero in this limited historical sample; that is an observation about recorded jobs, not evidence that the cache is unsound.
